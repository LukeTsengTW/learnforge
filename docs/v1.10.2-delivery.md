## Request and scope

v1.10.1 結案後，human 問是否建議把手寫上限改成無上限。建議是不要，理由是本機暫存、重畫成本、每次儲存都送整份草稿與 server 端 rasterize 都隨筆畫成長；並提出三步：先精簡取樣點、加上剩餘容量提示、仍不夠再提高上限。Human 要求先試第一步。

本次只做第一步。不在範圍內：容量提示、調整任何上限、drawing schema、server、座標取整。

當時對 human 的描述是「略過距離極近的點」。實作比這個描述多一點：它以容許誤差為準精簡折線，同一條直線上相距較遠（24 個邏輯單位以內）的取樣也會被略過。兩者都是精簡取樣點，這裡以實作為準。

## Investigation

- v1.10.1 的 DrawingCanvas 對每一個 pointer 事件（pointermove 與 pointerup）各存一個點，座標是沒有取整的浮點數，沒有任何篩選。
- 儲存上限有兩個彼此獨立的數字：每題 256 筆、6000 個取樣點（另有 geometry 預算）。精簡取樣點只在取樣點先滿時有幫助。
- 取樣密度取決於裝置的事件頻率與落筆速度。沒有實機錄製資料可以直接量測，所以用合成的手寫模型估計（見 Measurement）。

## Algorithm

`src/lib/stroke-sampling.ts` 的 `appendStrokeSample(points, run, sample)`。進行中的筆畫有兩個陣列：

- `points`：到目前為止保留的點，加上最新的取樣。它既是畫布上畫的，也是此刻 commit 會保存的。
- `run`：上一個保留點之後收到的取樣。

每來一個取樣：若「上一個保留點到這個取樣」的線段同時滿足下面三個條件，就用這個取樣取代 `points` 的最後一點；否則前一個取樣成為保留點，這個取樣接在後面。

| 常數 | 值 | 意義 |
|---|---|---|
| `STROKE_SAMPLE_TOLERANCE` | 0.5 | run 裡每一個取樣到這條線段的距離都不超過它。單位是邏輯單位，也就是顯示、儲存與 rasterize 所用的那張圖的像素；0.5 是半個像素 |
| `STROKE_SAMPLE_MAX_SEGMENT` | 24 | 這條線段不比它長。相距更遠的取樣照原樣保存，所以只有密集的取樣會被精簡 |
| `STROKE_SAMPLE_MAX_RUN` | 128 | run 的長度上限，用來限制每個事件的計算量；超過就多保留一個點 |

距離是到線段，不是到無限延伸的直線，所以沿原路折返的筆畫會保留折返點。

由此得到的性質：

1. 保存的點都是實際收到的取樣，順序不變，沒有重複保存。
2. 筆畫的第一點是落筆點，最後一點永遠是最新的取樣；放開時是抬筆點。
3. 每一個沒有保存的取樣，距保存的筆畫不超過 0.5。Independent reviewer 另外確認了反方向：保存的線段距原始路徑也不超過 0.5。
4. 畫布在筆畫進行中畫的就是 `points`，commit、cancel、失去 capture、切換作答方式或提交時的 flush 保存的也是同一個陣列。所以 v1.10.1 的 contract「正式提交的手寫內容等於畫布上已完成的筆跡」不變，任何時刻畫面與會被保存的內容都相同。
5. 用少數、相距超過 24 個邏輯單位的事件畫出的筆畫，保存結果與 v1.10.1 相同；點一下仍是兩個點。

`DrawingCanvas.tsx` 的變更是三個呼叫點：pointerdown 建立 `run`，pointermove 與 pointerup 由 `points.push` 改為呼叫 `appendStrokeSample`。繪製、commit、cancel、flush 的程式沒有改。橡皮擦筆畫走同一條路徑。

## What does not change

- 每題 256 筆、6000 個取樣點與 geometry 預算的上限，以及超過時的行為與提示。
- Drawing schema 與保存格式（`tool`／`color`／`width`／`points`）；座標仍是沒有取整的浮點數，每個點的大小不變。
- 已經保存的圖：不會被重新精簡，重播結果不變。
- 草稿儲存、正式提交、評分與 result／history 重建的流程。
- Server、migration、Edge function、題庫與 generated canonical context。
- Server 的 geometry 預算不會因為精簡而被新觸發：independent reviewer 以 server 的同一個外接矩形公式比較，保存後的總和相對原始取樣最差為 1.02 倍，其餘情況更低；最長線段的限制讓單段外接矩形有上限。

## Measurement

120 Hz 觸控筆、一般速度這一組的序列化大小由 384 KiB 降為 137 KiB。

### 真實的指標事件

本機 browser gate 以 Playwright 逐點移動滑鼠，頁面收到的是真正的 pointer 事件；畫布上另掛一個只做記錄的 listener，取得實際收到的每個取樣。這些是自動化產生的路徑，不是手寫。

- 圓、波浪、直角折線三筆（取樣間距約 1 個邏輯單位，小數座標）：863 個取樣存成 77 點，序列化 40,163 → 3,687 bytes。
- 同樣的路徑以整數 CSS 像素送出：1440 寬為 863 → 361 點，360 寬為 863 → 200 點。
- 稀疏的 6 步直線兩筆：8 → 8 點，沒有變化。
- 畫筆 502 → 81 點，橡皮擦 317 → 24 點，工具不變。
- 單一 6,601 個取樣的螺旋：存成 773 點並被接受；在 v1.10.1 會被取樣點上限拒絕。

所有情境中，收到的取樣距保存筆畫的最大距離不超過 0.5。

### 參數的選擇

0.5 與 24 是判斷，不是實機量測得到的結果。

容許誤差：以同一份合成資料（120 Hz 觸控筆、一般速度）在 1200×900 的畫布上以筆寬 4 重畫，與未精簡的圖逐像素比較。

| 容許誤差 | 倍率 | 墨跡像素中跨過 50% 覆蓋的比例 | 最大 alpha 差（0–255） |
|---|---|---|---|
| 0.25 | 1.64× | 1.1% | 112 |
| 0.5 | 3.0× | 6.2% | 164 |
| 0.75 | 5.2× | 10.1% | 209 |
| 1.0 | 6.6× | 13.7% | 255 |

實際採用的規則（0.5、最長線段 24）：56,573 個墨跡像素中 3,501 個跨過 50% 覆蓋，其中 9 個不在原圖邊緣 1 像素的範圍內；縮小一半後最大差 92／255。放大 5 倍對照，0.75 與 1.0 的曲線開始出現稜角，0.5 與未精簡的圖看不出差別；這是目視判斷，不是量測過的感知結果。

最長線段：這條規則是在第一版實作之後才加入的。沒有它時有 43 個既有測試的預期值改變——它們用三點共線、彼此相距數十到一百多個邏輯單位的筆畫比對精確的點列。加上 24 的限制後，這類稀疏的輸入照原樣保存，模型中的代價不到 1%（3,848 → 3,857 點）。這條規則本身的理由是：只有密集的取樣才精簡；進行中的最後一段能被修正的範圍有上限；server 的 geometry 外接矩形有上限。數值選在不改變那些測試的輸入的範圍內。

## Capacity after this change

256 筆的上限沒有改變。上表中，精簡之後多數情況先碰到的是筆數上限，不再是取樣點上限。所以這次變更解決的是「取樣點先滿」，對「筆數滿」沒有幫助；筆畫多的手寫推導仍會碰到上限並看到提示。提高筆數上限需要同時修改資料庫的檢查與 Edge function，屬於另行決定的範圍。

## Known limitations

- **效益的數字來自合成的手寫模型與自動化的滑鼠路徑。** 沒有 iPad、Apple Pencil 或觸控的實機錄製與驗證；實際裝置上的取樣密度、座標精度與書寫速度可能與模型不同，倍率也會不同。
- **256 筆的上限沒有改變**，在多數模型情況下會變成先碰到的限制。筆畫多的手寫推導仍會碰到上限；提高它需要 migration 與 human 的決定。
- 容許誤差 0.5 與最長線段 24 是判斷。「看不出差別」是對放大對照圖與像素統計的判讀，不是量測過的感知結果。
- AI 評分所見的圖（server 以保存的筆畫 rasterize）可能在邊緣像素上與未精簡時不同。沒有呼叫 provider 比較過評分結果。
- 筆畫進行中，最後一段會隨著筆的移動被修正，幅度不超過 0.5 個邏輯單位、長度不超過 24。
- 已經保存的圖不會被重新精簡；每個點的大小沒有變（座標仍是未取整的浮點數）。
- 筆停在原地不動時，每 128 個取樣仍會多存一個點。
- Author Preview 與畫圖題使用同一個畫布，同樣受這次變更影響。
- 既有行為，與本次變更無關：筆畫進行中若失去 pointer capture，畫布會就地 commit 當時的筆畫，同一個手勢之後的取樣不再納入，直到放開再落筆；畫布與保存的內容仍然一致，沒有提示。Independent reviewer 在一次瀏覽器執行中觀察到一筆筆畫只存到中途（之後重跑五次都完整，原因無法確定），並在本 candidate 與 v1.10.1 的 build 上強制釋放 capture 得到相同的結果。
