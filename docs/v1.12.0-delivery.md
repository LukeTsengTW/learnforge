## Request and scope

Human 的需求：按下提交測驗按鈕時，新增提交的進度條，顯示已提交哪些項目，讓使用者不會因為等很久以為當掉而離開網頁；完成後以 sub-agent 做 review，並透過 Playwright 測試，需要登入時通知 human。之後 human 要求先以 release-canary 帳號在 production 實際提交一次，沒有問題就發版。

「已提交哪些項目」以提交流程的步驟呈現。逐題的評分進度不在範圍內，理由見下一節；本版只改 frontend。

## Investigation

- 正式提交由 practice store 的 `submit()` 執行，依序為：等待進行中的同步並儲存最新草稿（必要時 save-quiz-draft）、重新讀取草稿確認 CAS、呼叫 submit-quiz（伺服器回覆 `in_progress` 時每 1.5 秒重試，最多 40 次）、讀取已提交的作答。原本提交中只在表單上方顯示「正在檢查填空題答案語意…」：它只描述填空題，而且按下提交的位置（頁面底部）看不到。
- 伺服器在同一個 submit-quiz 請求內依序評分各題（填空題的規則判定，必要時 AI；計算與畫圖題的 rubric）。`fill_judgments` 與 `rubric_judgments` 的 RLS 只在作答狀態為 submitted 時允許使用者讀取（`20260928043551_semantic_fill_submission.sql`、`20260928143200_ai_grading_v3_submission.sql`），所以評分途中前端無法得知哪些題目已評完。逐題進度需要後端變更（例如新的進度端點或串流回應），不在本版。

## Design

- `attempt-context.ts`：新增 `SUBMIT_STAGES`（save／verify／grade／result）與 `SubmitProgress`（stage、startedAt、waiting），`AttemptContextValue` 多一個選用的 `submitProgress`。
- `practice-store.ts`：`submit()` 在各階段開始時發布步驟（開始時 save；重新讀取草稿前 verify；呼叫 submit-quiz 前 grade；伺服器第一次回覆 `in_progress` 時 waiting；收到已提交的回應後 result），結束時（成功或失敗）清除。只發布 snapshot，不增加任何 repository 呼叫；提交的界線、CAS、request id 與錯誤處理不變。
- `PracticeQuizRoute.tsx`：把 `submitProgress` 傳進 context。舊的 `AttemptProvider`／`CloudAttemptProvider` 不回報步驟。
- `SubmitProgress.tsx`（新）與 `QuizPage.tsx`：
  - 提交中，畫面底部固定顯示「正在提交測驗」卡片：進度條（`aria-valuetext` 為「第 n 步，共 4 步」）、每秒更新的「已經過 m:ss」、四個步驟與狀態（完成／進行中／等待）、「完成後會自動前往結果頁。請保持此頁面開啟，不要重新整理或關閉。」。固定位置讓以 Enter 由頁面中段提交時也看得到。
  - 目前步驟的說明：儲存時「已作答 n / N 題」；評分時列出這份題庫中實際含有、可能需要 AI 評分的題型（填空題、計算題、畫圖題，名稱與題目卡片相同），沒有這些題型時為「由系統自動評分。」；等待時「這份作答已有評分正在進行，正在等待結果。」（可能是同一頁先前的請求，也可能是另一個分頁或裝置）。
  - 只有步驟那一行是 live region，等待時加上「（等待進行中的評分）」；時間不在 live region 內。目前步驟為 `aria-current="step"`。減少動態效果的設定由既有的全域規則停用轉圈動畫。
  - 提交沒有完成而且有通知時，提交區（不是固定位置）顯示「提交未完成」與通知的原文，原因是它的 accessible description；它出現時取得焦點並捲動到可見處；「知道了」關閉並把焦點交回「提交測驗」。答案被接受、再按一次提交，或通知消失時，它也會消失；通知消失後再出現新的通知，它不會回來（避免搶走焦點）。
  - 按下提交後「仍然提交」的確認框隨即關閉；移除表單上方的「正在檢查填空題答案語意…」。
- `global.css`：卡片與步驟的樣式只用既有的主題 token（深色主題的完成圖示用 `--primary`／`--on-primary` 以維持對比）；`max-height` 先寫 `100vh` 再寫 `100svh`；360 寬時縮小邊距。

## Browser evidence

本機受控 fixture：真正的 application、routes、practice store 與 QuizPage，記憶體內的假 server 可以暫停任一次讀取、儲存或提交、回覆 `pending`，或讓下一次提交失敗。網站由 Playwright 從磁碟提供，request 只有對 127.0.0.1 的 GET，沒有 socket。Chromium headless shell。

- 四個步驟：暫停各階段的呼叫，依序看到步驟 1／2／3／4 與完成標記；計時由 0:00 前進到 0:02；提交按鈕鎖定；完成後前往結果頁、卡片消失。
- 等待中的評分：伺服器回覆兩次 `pending`，看到等待的說明與 live 行的附註，之後完成。
- 失敗：「提交未完成」位於提交區、取得焦點、與頁面上方的通知相同；答案被接受時消失；「知道了」後焦點回到「提交測驗」；再按提交時消失並出現確認框；重試後提交成功。
- 在填空題輸入框按 Enter（客觀題都已作答）：由頁面中段直接提交，卡片完整在畫面內。
- 1440／768／360（淺色）與 360（深色）：卡片與「提交未完成」都在畫面內，頁面與卡片都沒有水平 overflow；深色主題的顏色來自 token。
- 減少動態效果：轉圈動畫為 none，計時仍前進。
- Console errors、page errors、unhandled rejections：0。

## Review

Review 由本 session 內的 sub-agent（code reviewer）執行，不是過去的 `learnforge-reviewer` peer session（當時沒有在執行）。

- Cycle 1：沒有 blocking，8 項發現。修正 7 項：提交未完成的卡片在手機上蓋住提交按鈕（改放在提交區）、失敗時沒有朗讀也沒有焦點（改為取得焦點）、題型名稱與題目卡片不一致、等待的文字不精確、等待沒有朗讀、缺少的測試、`svh` 沒有 fallback。第 8 項（「提交未完成」顯示頁面當下的通知）reviewer 同意低優先，保留並列入已知限制。Reviewer 另指出一個既有行為（提交中離開頁面，評分完成後仍會前往結果頁），也列入已知限制。
- Cycle 2：7 項皆確認解決。另提 3 個 nit（原因作為 accessible description、通知消失後再出現時不應搶焦點、一處測試註解），也已修正；修正後重跑全部 gates 與 browser。這 3 個 nit 的修正由 release-prep review 確認。
- Release-prep review（同一個 sub-agent）：見 post-commit report。

## Authenticated production canary（提交前）

依 human 的要求，在發版前以 production backend 實際提交一次。登入請求中列出兩個方案：A 只作答選擇與是非題，不需要 AI 評分；B 另外作答一題計算題，會觸發一次付費 AI 評分。並說明只回覆「登入完成」視為 A。Human 回覆「登入完成」，因此執行 A。

做法：

- Candidate 的 working tree 以 production 的 client 設定建置，base 為 `/`（Pages 的 build 為 `/learnforge/`），navigation 仍為 v1.11.0，因為版本號是在 canary 之後才改；由本機 `127.0.0.1:4173` 提供。提供的 index 與它引用的 8 個檔案與 build 逐位元組相同，沒有被注入的內容；CSP 的 connect-src 只有本身、production backend 與 Turnstile。
- Human 在一般啟動的 Chrome（全新的暫存 profile，remote debugging 只綁 127.0.0.1）手動完成 Turnstile 並登入既有的專用 release-canary 帳號；登入完成後才以 CDP attach。
- Attach 時先裝上 fail-closed 的 request guard：provider-facing function 一律阻擋；POST 只允許 session 維護、`account-recovery-code` 的 status、通過身分檢查後的 canary 題庫草稿、只含宣告答案的 save-quiz-draft，以及一次綁定到最後一次被接受的儲存、且與頁面上的答案相同的 submit-quiz。紀錄只保留時間、method、host、pathname、status 與推導出的事實。
- 先在本機以同一組 script 對模擬 production API 的 harness 排練：方案 A 與 B 各一次完成；練習紀錄多一筆、或 demo 已有草稿時，身分檢查失敗且沒有任何寫入。

結果：

- 身分（只讀 UI）：練習紀錄 3 筆，依序為 離散數學第一章：計數的基本原理－例題練習（版本 1，0 / 150）、2025 Discrete Mathematics 期中考（版本 2，0 / 100）、數位邏輯與基礎數學（版本 v2-handwriting，1 / 20）；Library 只有 `discrete-math-ch3-set-theory-examples` 與 `discrete-math-exercises-2026` 是「繼續作答」；demo 為「開始練習」；頁面是含提交進度卡片的 candidate build。
- 開啟 `demo`／v2-handwriting：建立一份草稿（rpc 1 次），伺服器讀回的草稿沒有任何答案，頁面為 0 / 7。
- 作答 q1–q4：save-quiz-draft 1 次，200，schema 2；伺服器讀回 q1–q4 與宣告的答案相同；頁面 4 / 7。
- 提交：確認框「還有 1 題自動評分題未作答。」→ 仍然提交。Guard 的 8 項檢查全部成立，submit-quiz 1 次，200，`ai-grading-v4`，`cached: false`。卡片在畫面內依序出現（以開始記錄、也就是按下「提交測驗」之前為 0 的毫秒數）：121 步驟 1／4、276 步驟 2／4、420 步驟 3／4（評分說明列出填空題、計算題、畫圖題）、1178 步驟 4／4、1527 卡片消失並前往結果頁；評分步驟約 0.76 秒。評分步驟另存了一張只含卡片的截圖。
- 結果：8 / 20；q1–q4 correct、q5 unanswered；q6、q7 為 system/unanswered，score 0；AI 評分 0；結果頁「正確 4、部分得分 0、錯誤 0、未作答 3」。伺服器讀回的已提交作答為 q1–q4、8 / 20。
- 之後（只讀 UI）：練習紀錄 4 筆，新的一筆在最上面（數位邏輯與基礎數學，版本 v2-handwriting，8 / 20），其餘 3 筆不變；Library 的「繼續作答」仍只在兩份保留草稿；demo 回到「開始練習」。
- Request：backend 29 個、本機 1 個（為了確認 build 而讀取主要的 JS）；GET 26、POST 4。POST 為 `account-recovery-code` 1（status，由 app 自動送出）、`rpc/get_or_create_quiz_draft` 1、`save-quiz-draft` 1、`submit-quiz` 1，全部 200。GET 包含 `functions/v1/ai-quota` 2 次與 `ai-responses` 2 次（開啟練習頁時 app 自動送出）。Provider-facing function 的 request 0；guard 阻擋 0；HTTP 錯誤 0；console／page errors 0；CSP violations 0。
- 清理：以 CDP 關閉 Chrome，刪除暫存 profile（裡面有 session），停止本機的伺服器。沒有登出（登出是 Auth 的寫入）。

Production 資料的變更：觀察到的寫入 request 是上面 4 個 POST。以下依程式碼推定（submit-quiz handler 與 migrations；沒有以 SQL 讀取）：伺服器新增一份草稿並寫入 q1–q4 的答案列。正式提交時，q6（空白的計算題）以 system-unanswered 的方式查詢，`claim_rubric_judgment_v4` 直接回傳 unanswered，不寫入任何列。q7（空白的畫圖題）走一般的 claim：新增 `private.rubric_judge_cache` 與 `private.rubric_judge_calls` 各一列（reserved），server rasterize 判定為空白後，`fail_rubric_judgment` 把兩列標為 failed（`raster_blank`）；這一列 calls 計入 rubric 呼叫在 24 小時內每份作答 20 次、每個使用者 100 次的上限。最後保存 q5 的規則判定、q6／q7 的 system/unanswered 評分紀錄，並把作答改為 submitted。`ai-quota` 的讀取會把這個使用者過期的 reservation 標記為過期，受影響的列數不知道。沒有付費的 provider 呼叫：評分結果沒有 AI 判定，而且 provider-facing function 沒有被呼叫。

這次 canary 的範圍：它驗到 candidate 的程式碼在 production backend 上依序顯示四個步驟並完成提交。它沒有驗到：Pages 部署上的同一件事（部署後另做未登入的驗收與 bundle 檢查）、需要數十秒以上的 AI 評分時卡片的樣子（只有本機以 4 秒模擬）、等待中的評分與提交失敗在 production 的樣子。

## Risk, classifier and provider canary

`release:classify --base v1.11.0 --head HEAD --include-working-tree`：**security-ai／Risk C／providerCanaryRequired=false**。Risk C 來自本機 ignored 的 `.env.local` 與 package files 的 unrecognized path；所有 source 與測試路徑都是 frontend or domain behavior，`global.css` 是 frontend presentation。沒有 migration、Edge function 或 generated context 的變更，不需要 backend 同步。Provider canary：不需要，未執行；canary 沒有付費的 provider 呼叫。

### 登入後 smoke 的替代

`docs/release-process.md` 要求 frontend 行為的變更在部署後另做登入後的唯讀 smoke，而且較高風險的 release 不能略過較低風險的 gate。本版**不在 Pages 部署後再請 human 登入**，改以下列組合替代：

- 部署前的登入後 canary（上一節）：candidate 的程式碼在 production backend 上真正走過一次草稿建立、儲存與正式提交，比唯讀 smoke 涵蓋得更多。
- 部署後：release.json 的 version 為 1.12.0、gitSha 等於 candidate commit；canonical public smoke；部署的主要 JS 含有「正在提交測驗」、「提交未完成」與 `submit-stopped-reason`。
- Canary 之後到 candidate commit 之間，runtime source 只改了 `Layout.tsx` 的版本字樣（其餘是 package files 與文件）；backend、Auth 與 CORS 都沒有變更。

這個替代沒有涵蓋：Pages 的 origin 與 `/learnforge/` base 下的登入 session、CI 建置的 artifact 本身在登入後的行為。Release-prep review 核定這個替代可以接受；v1.10.2 也曾由 release review 核定略過登入後的 canary。

## Known limitations

- 步驟是瀏覽器端的階段，不是逐題評分進度。AI 評分較久時會停在「評分作答」一段時間；卡片以計時與說明表示仍在進行。逐題進度需要後端變更。
- 提交進行中沒有離開頁面的提醒（`beforeunload`）。提交中透過 header 的連結離開時，評分完成後仍會前往結果頁（既有行為）。
- 「提交未完成」顯示的是頁面當下的通知；之後若出現其他同步通知，它顯示的是那則通知（「尚未提交」仍然成立）。
- 舊的 `AttemptProvider`／`CloudAttemptProvider` 不回報步驟（目前只在測試中使用）。
- Browser 證據是桌面的 Chromium headless shell；沒有 iPad 或其他行動裝置的實機驗證。
- Production canary 在本機提供的 candidate 上執行，不是在 Pages 部署上；只走了不需要 AI 的評分（約 0.76 秒）。Canary 帳號多了一筆已提交的作答，沒有 cleanup。
