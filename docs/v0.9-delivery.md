## 2. Analytics architecture

`AnalyticsAttempt` is a narrow submitted-history projection, separate from `QuizAttempt`. `buildLearningAnalytics()` and the subject, tag, type, trend and review helpers are pure. The page receives one bounded cloud snapshot and renders the returned `LearningAnalytics`; it does not group rows in React. The same input rows, bundled quiz revisions and current-quiz lookup produce the same output. Dates are compared by parsed instant, with stable attempt-ID / key tie breaks.

## 3. Data loading

`listSubmittedAnalyticsPage()` queries 50 submitted attempts plus one lookahead row, ordered by `submitted_at DESC, id DESC` and filtered by `user_id`. It then queries answers once for the first 50 attempt IDs, also filtered by `user_id`. `scanLearningHistory()` reads up to 10 pages / 500 attempts. It exposes `scannedAttemptCount` and `isTruncated`; the UI shows loading progress and the 500-attempt notice. A failed cloud page results in an unavailable state, never a partial result presented as complete history. Historical missing revisions and malformed rows are countable exclusions.

## 4. Deterministic regrading

For each valid submitted row, `fromDatabase()` validates answers against its exact `quiz_id + quiz_revision` and recomputes the canonical result. The pure analytics engine calls the existing `gradeQuiz()` again using those validated answers. Neither `answers.grade` nor `attempts.deterministic_*` is an analytics source. A missing revision is excluded without substituting the current quiz.

## 5. Objective / manual separation

Only `single`, `multiple`, `true-false` and `fill` create `ObjectiveOccurrence`. `calculation` and `drawing` contribute only to `manualQuestionSubmissions`; their points and AI advisory grades never enter accuracy, completion, points, topic statistics or trend. This field uses `gradeQuiz().manualCount`: it counts manual question occurrences in submitted quizzes even when the student left those questions blank, not the number of written or drawn responses. The analytics and review paths import no Tutor or OpenAI service and create no AI request.

## 6. Overall metrics

Overview shows completed submissions, objective question occurrences, answered objective occurrences, correct, incorrect, unanswered, answered accuracy, completion rate and objective-only points earned / available. Answered accuracy is `correct / (correct + incorrect)`; completion is `(correct + incorrect) / (correct + incorrect + unanswered)`. Empty denominators render `—`, not 0%.

## 7. Subject analytics

Valid submitted attempts aggregate by the exact revision's `Quiz.subject`. Each subject has attempt count, answered, correct, incorrect, unanswered, answered accuracy and most recent practice time. Cards sort by most recent time, then stable subject name.

## 8. Tag analytics

Question tags are used when present; otherwise quiz tags are the fallback. Tags are trimmed, lowercased and deduplicated within each occurrence. A multi-tag question contributes once to each tag, intentionally. Each tag card shows total sample, answered, correct, incorrect, unanswered, accuracy and most recent occurrence.

## 9. Topic signal

Fewer than three answered occurrences means `資料不足`. At three or more: accuracy ≥80% is `表現穩定`, 60–79% is `持續練習`, and <60% is `需要複習`. Constants live together in `learning-analytics.ts`; these are transparent product hints, not psychometric or official mastery scores.

## 10. Question-type analytics

The four objective types appear in fixed order with answered, correct, incorrect, unanswered and accuracy. Manual types are not in the accuracy list.

## 11. Weekly trend

Eight UTC Monday–Sunday weeks end at the week of the most recent analyzable objective occurrence. Each point has answered, correct and accuracy. An empty week has accuracy `null` / `—`, and the UI states the UTC policy. Tests cover a UTC week boundary and empty weeks.

## 12. Review queue

`buildReviewQueue()` groups objective occurrences by the stable conceptual pair `quizId + questionId`. The queue contains one item per pair whose latest resolvable occurrence is incorrect. Items include exact historical quiz/question, tags, subject, type, incorrect count, latest wrong time and last student answer in memory. The canonical solution is not rendered before the review check.

## 13. Latest-outcome semantics

A later correct submission removes an earlier mistake. A later incorrect submission puts the question in the queue. A latest unanswered objective occurrence is outside the wrong-answer queue. Same-time occurrences use stable attempt ID; queue display sorts by latest wrong time, then key. `#/mistakes` continues to show historical wrong events, while `#/review` is the deduplicated current queue.

## 14. Revision handling

The queue item retains the exact revision of its latest incorrect occurrence. Review uses that historical question even when the current bundled revision differs; the UI notes both revision IDs, offers a control to focus the historical question, and links to the current full quiz. A revision absent from the bundle is counted as unavailable and never silently upgraded.

## 15. Focused retry

The review page shows one objective question at a time using existing `QuestionCard` / `QuestionInput`, Markdown and KaTeX. `檢查答案` calls the formal deterministic grader on that exact one-question historical quiz. `ResultQuestion` then shows the student's answer, correct answer and solution. `再試一次` clears the answer and hides the solution; session counters are React memory only. A refresh resets session progress and rederives the persistent queue from formal submissions. No `PracticeAttempt`, `saveDraft()` or Supabase write is used by the review component.

## 16. History / Mistakes integration

History links to analytics and review; Mistakes links to review and analytics. Home has signed-in entry points without scanning history. The header groups analytics, review and AI usage under `更多學習`, while the existing History and Mistakes routes remain available.

## 17. Query performance

It was removed immediately afterward; `src/main.tsx` has no retained trace code. The trace contains no session token, Authorization header, user ID, attempt ID, request body or answer data.

## 18. Database / index changes

No database change or migration was needed. A live read-only `pg_indexes` query on `learnforge-demo` confirmed `attempts_history_idx ON attempts(user_id, submitted_at DESC, id DESC) WHERE status='submitted'`, `answers_attempt_id_question_id_key ON answers(attempt_id, question_id)` and `answers_user_id_idx ON answers(user_id)`. The attempts index predicate and key order align with the bounded analytics query; the answers index starts with the batch filter column. Existing RLS and explicit owner filters remain in force.

Two representative `EXPLAIN (FORMAT TEXT)` statements used the dedicated test account, resolving its user ID from the newly submitted test attempt and using the two known test attempt IDs for the answers batch. They did **not** use `ANALYZE`, modify data, change planner settings or create an index. The attempts plan was `Limit → Sort → Seq Scan on attempts` with an additional `Seq Scan` InitPlan to resolve the owner; it applied `user_id` and `status='submitted'` filters. The answers plan was `Seq Scan on answers` with `attempt_id = ANY(two IDs)` and `user_id` filters, plus the owner InitPlan. At this tiny table size the planner chose sequential scans, so the live plan does not prove the index will be chosen at larger scale. Index compatibility is established by the live definition and query shape; production-scale performance remains unmeasured.

## 20. Security

The mapper rejects a foreign attempt or mismatched answer as an invalid security boundary, rather than silently counting it as malformed. No service-role key, new privileged function, data warehouse, or duplicated analytics table was added. Student answers and full analytics data are not logged or sent to OpenAI.

## 28. Limitations

Only the newest 500 submitted attempts are analyzed; older outcomes do not affect the v0.9 queue. Review session state resets on refresh. The browser trace covers one two-attempt batch of application `fetch` calls, not a large data set or all browser network traffic. The live `EXPLAIN` plans chose sequential scans on the tiny current tables; larger-scale index choice and latency remain unverified. Existing mistakes history remains page-by-page. Analytics depends on a complete cloud read and intentionally provides no offline partial approximation.

## 29. Recommended v1.0

Prioritize account recovery, abuse protection and sync/recovery UX. After collecting larger real history sizes, repeat the browser trace and `EXPLAIN` with representative volume before changing the 500-attempt window or read strategy. Keep deterministic grading and existing submissions as the sole performance source.
