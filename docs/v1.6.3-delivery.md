## Narrow fix

- Pointerup appends the final point and commits. Pointercancel commits existing partial points without appending cancellation coordinates. Both rely on browser implicit capture release.
- Lost capture is a recovery handler: it only terminates the matching pending stroke when hasPointerCapture is false. A new capture for the reused ID makes an old notification a no-op.
- Imperative flush commits/clears pending before explicit release, preventing reentrant or later capture-loss duplicate commits; an idle flush returns the latest locally committed strokes.
- A synchronous committed-strokes ref drives reducer additions and canvas replay before parent acknowledgement. Local visible state supports tools/export while waiting. A changed controlled strokes identity reconciles authoritatively, including replacement/clear. Parent acknowledgement replays committed plus active pending ink. No stroke schema changes, timers, throttling or delayed pointerdown.
- Undo/redo/clear repaint the emitted local state immediately; PNG uses the visible committed history. Existing parent-controlled integration and answer-mode flush contract remain intact.

The capture assumptions were checked against [W3C Pointer Events: Element capture APIs](https://www.w3.org/TR/pointerevents3/#extensions-to-the-element-interface) and [implicit release](https://www.w3.org/TR/pointerevents3/#implicit-release-of-pointer-capture): hasPointerCapture reflects pending capture immediately after setPointerCapture; the UA releases after up/cancel.

## Physical iPad / Apple Pencil compatibility finding (user reported 2026-10-07)

On diagnostic candidate `87b6b5d87b6302c4be5e7301771a698f3d9b0e7d`, the user's actual iPad + Apple Pencil reproduced rapid re-contact failure with iPadOS Scribble /「隨手寫」enabled. The prior stroke completed normally: pointerup → UP_COMMIT → pending cleared → lostpointercapture. During the failed sub-second next contact, the page received neither Pencil pointerdown nor stylus touchstart. This contact therefore did not reach LearnForge's primary/pending/capture/input-mode guards or renderer. This finding is not a LearnForge pointer-handler regression.

Disabling Scribble eliminated the observed failure for the same rapid discontinuous handwriting in the user's physical-device control. Record this evidence as **REAL APPLE PENCIL PASS WITH SCRIBBLE DISABLED (diagnostic candidate; user-reported control)**. This does not claim Scribble-enabled handwriting is fixed, or establish a universal Safari/WebKit defect. Raw trace/device version metadata were not supplied in this continuation; the event conclusion is attributed to the user's hardware report.

The page cannot recover a contact that iPadOS/Safari never delivers. No timing workaround, retry timer, synthesized stroke, Touch fallback, or speculative removal of isPrimary is included.

Apple's [official Taiwan Scribble instructions](https://support.apple.com/zh-tw/guide/ipad/ipad355ab2a7/ipados) confirm **設定 > Apple Pencil > 隨手寫** as the setting path. The web app cannot inspect whether that setting is currently enabled.
