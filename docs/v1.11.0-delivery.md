## Request and scope

v1.10.2 結案報告向 human 列了剩下的三步：剩餘容量提示、提高筆數或取樣點上限（需要 migration 與重新部署 Edge function）、座標取整以縮小每個點的大小。Human 附上兩張 iPad 實際操作的畫面後回覆：「這兩張是實際操作的圖片，寫到一半就因筆數上限無法繼續寫下去了，所以接下來做剩下的那幾步。」畫面中的手寫大約寫到畫布的四到五成就被 256 筆的上限擋下。

在提出新的上限數字之前，human 追加了一個設計分析階段：「我不想只單純決定『256 要改成多少』」，要求評估能否把固定的筆數上限由主要的容量限制改成只防濫用的 hard cap，日常容量改由序列化大小、取樣點、raster 與 geometry 成本決定；不得降低 server 的 DoS 防護、raster 安全、既有圖的相容性與復原／橡皮擦／重播的語意；不得用合併不相連筆畫這類會改變 raster 語意的做法；先對 256／512／1024／2048 筆量測瀏覽器互動、序列化大小、解析、server rasterize、草稿儲存與提交 payload，再判斷是「現有 schema 下就能改」「必須 migration」還是「必須重新設計 schema」。並要求 v1.10.1 的修正不能退回：畫布顯示的內容與作答、提交的狀態必須永遠一致。

範圍（由 independent reviewer 逐項裁定）：

- Human 的三步：容量提示、提高上限、座標取整。
- 三步之外、為了讓放寬後的上限可以安全使用而納入的四項：整份草稿的大小改在接受變更時檢查；拒絕訊息依上限分開；筆畫進行中的畫法；被接受的一筆只重畫一次。前三項在實作前告知 human，沒有收到反對。
- 不在範圍內：同步的時機與協定（每次停筆仍上傳整份草稿）、資料庫每次儲存重寫全部答案列、整份草稿 4 MiB 的上限、geometry 預算、PNG 大小上限、畫布尺寸上限、drawing schema。

## Design analysis and conclusion

結論是「必須 migration，而且是最小的那一種」。現有 schema 不需要重新設計：筆畫的保存格式（`tool`／`color`／`width`／`points`）不變。只靠前端與 Edge function 不夠，因為資料庫的 `private.v4_strokes_shape_valid` 把 256 與 6000 寫死在函式裡。這個函式在正式提交時由 `public.finalize_ai_grading_v4_submission` 對每一個保存的答案執行；超過它的上限時，保存的答案被判定為無效，提交失敗。草稿儲存不經過它：儲存時逐題檢查的是 save-quiz-draft 這個 Edge function，資料庫的 `public.save_quiz_attempt_v4` 只檢查整體大小與 key 並重寫答案列。所以若只放寬前端與 Edge，超過舊上限的手寫存得進草稿，卻交不出去。Migration 只改這個函式的兩個數字。

採用以資源為準的預算：

| 項目 | v1.10.2 | v1.11.0 | 檢查的地方 |
|---|---|---|---|
| 每題取樣點 | 6,000 | 32,000 | 前端、Edge、資料庫函式（正式提交時） |
| 每題筆數 | 256 | 16,000（只防濫用） | 前端、Edge、資料庫函式（正式提交時） |
| 每題 geometry（rasterizer 走訪的像素） | 25,000,000 | 不變 | 前端、Edge |
| PNG 大小 | 2,000,000 bytes | 不變 | Edge |
| 畫布邊長 | 1200 | 不變 | Edge |
| 整份草稿的答案 | 4 MiB（4,194,304 bytes）、100 題 | 不變；改為在接受變更時就檢查 | 前端（新）、Edge |

日常書寫先碰到的是取樣點與 geometry，其次是整份草稿的大小。筆數 16,000 不是容量的單位：正常落筆到抬筆的一筆至少保存兩個點（點一下是兩個點），16,000 筆這樣的筆畫至少是 32,000 個點，所以正常書寫下取樣點預算先到。例外是只有一個點的筆畫：落筆後還沒移動就被 cancel、失去 pointer capture 或被 flush（例如切換作答方式或按下提交）的那一筆。筆數上限擋的就是每筆一個點的資料，不論是這類例外累積而成，還是不經畫布直接送進來的；另一個理由是 rasterizer 以 16 位元的數字標記筆畫，筆數必須小於 65,536。兩個條件（小於 65,536、筆數的兩倍不超過取樣點預算）都有測試釘住。

32,000 這個數字的依據是量測（見 Measurement）：一題寫滿的合成手寫在 4,375 到 19,105 點之間；32,000 點的單一筆畫序列化後是 670 KiB，最不利的形狀（16,384 筆、每筆兩個點，略高於上限）是 1,555 KiB；這些形狀單題的 server 驗證、rasterize 與資料庫檢查在本機都在半秒以內。它是判斷，不是由實機資料推得的上界。

## Coordinate rounding

`toLogicalPoint` 把指標位置換算成邏輯座標並 clamp 之後，取整到 0.1 個邏輯單位（`DRAWING_COORDINATE_STEPS_PER_UNIT = 10`）。先 clamp 再取整，而畫布尺寸是整數，所以取整後的點不會離開畫布。每個軸的位移不超過 0.05，兩軸合計不超過 0.0707 個邏輯單位，遠小於顯示、儲存與 rasterize 所用那張圖的一個像素。

取整發生在取樣進入筆畫之前，所以畫布上畫的、精簡時比較的與保存的都是取整後的點。v1.10.2 的敘述因此要改寫：**保存的點都是「取整後的取樣」，每一個沒有保存的取整後取樣，距保存的筆畫不超過 0.5 個邏輯單位**。相對於取整前的指標位置，上限是 0.5 加上取整的位移。

效果是每個點的 JSON 大約減半（見 Measurement 的序列化大小）。已經保存的圖不會被重新取整；未取整的舊座標仍然合法，有測試以 256 筆、6000 個未取整的點確認新的 parser 與資料庫函式都接受。

## Painting a stroke in progress, and one replay per accepted stroke

v1.10.2 在筆畫進行中，每一次指標移動都重畫全部已完成的筆畫再畫進行中的這一筆，成本隨筆畫數成長。上限放寬之後，處理一次移動的時間若超過一個畫面更新，瀏覽器會合併指標移動，保存下來的筆畫就會少掉取樣。

現在已完成的筆畫保留成一張離屏的點陣圖；每次移動只把這張圖貼上，再畫進行中的這一筆（`paintInProgress`）。整個頁面共用一張離屏 canvas，因為同一時間只有一筆在進行，記憶體用量與題數無關。離屏的圖在下列情況重建：已完成的筆畫換成另一個陣列、改在另一張畫布上寫、畫布尺寸不同。取不到離屏 context、context 不能貼圖或貼圖丟出例外時，退回原本的完整重畫；指標事件的處理不會因此丟出例外。取樣與提交的程式沒有改：同樣的指標事件保存出逐值相同的筆畫，不論走哪一條畫法。

靜止時的畫布仍然是完整重畫的結果。放開一筆時，先把放開位置的取樣畫上去，再把這一筆交給作答的擁有者（練習頁的 practice store 或 Author Preview 的頁面狀態）：

- 擁有者接受：元件不再自己重畫一次；擁有者把新的筆畫交回來時，畫布依這份筆畫完整重畫一次，並更新離屏的圖。v1.10.2 這裡是兩次完整重畫。
- 擁有者拒絕：畫布立刻依已接受的筆畫完整重畫，被拒絕的這一筆（包含放開位置的取樣）不留在畫布上，並顯示原因。
- 復原、重做與清除：維持原本的做法。

v1.10.1 的 contract 不變：畫布只顯示答案已接受的筆跡，正式提交的手寫內容等於按下提交時畫布上已完成的筆跡。

## Capacity line and refusal notices

畫布下方新增一行容量提示。

- **何時出現**：四項限制（筆數、取樣點、geometry、整份草稿的大小）中最滿的一項達到 75%，或任何一項已經沒有一筆「一般筆畫」的餘裕。低於 75% 時不顯示。Author Preview 沒有草稿，只看前三項。
- **內容**：一般狀態是「手寫容量已用 N%（項目）。」；沒有餘裕時改為警示樣式的「手寫容量幾乎用完（項目），下一筆可能無法加入。」。項目會指出是哪一項：筆數與取樣點附上目前與上限的數字，另外兩項是「筆畫與橡皮擦的累計範圍」與「整份作答的大小」。
- **保證的定義**：提示行不是「幾乎用完」時，以目前選用的筆寬畫一筆一般筆畫，保證不會被任何一項上限拒絕。一般筆畫指保存後不超過 256 個點、相鄰兩點相距不超過 48 個邏輯單位；草稿大小為它保留 10,496 bytes。更長或更快的筆畫仍可能在提示行顯示有餘裕時被拒絕，訊息會指出是哪一項。橡皮擦越粗，需要的 geometry 餘裕越大，所以同一張圖換成粗橡皮擦後可能變成「幾乎用完」。
- **無障礙**：提示行不是 live region，不會每一筆都被讀出。由有餘裕變成沒有餘裕的那一筆，在既有的狀態列說一次「手寫容量幾乎用完。」。

75% 以下不顯示是實作時的選擇。Human 的原話是「剩餘容量提示」，沒有指定何時顯示。

拒絕訊息依原因分開，判斷的順序與 server 的 parser 相同（筆數、逐筆累計的取樣點、geometry）：

- 筆數：「這一筆沒有加入作答：這一題的手寫已達筆數的儲存上限（最多 16,000 筆）。請先復原或清除部分筆畫再繼續。」
- 取樣點：同樣的句型，「取樣點的儲存上限（最多 32,000 個取樣點）」。
- Geometry：指出是筆畫與橡皮擦的累計範圍，較粗的橡皮擦用得多時會先碰到，並建議改用較細的橡皮擦。
- 整份草稿：指出是整份作答的大小，任何一題復原或清除部分筆畫都可以。
- 擁有者拒絕但不屬於以上任何一項時，沿用一般的說法。

## Whole-draft size at accept time

v1.10.2 的整份草稿大小只在儲存時由 save-quiz-draft 檢查。上限放寬之後，幾題寫得多就可能超過 4 MiB；那時本機會先接受，之後同步失敗，訊息是「作答資料格式不符」。

現在 `answerQuizDraftV4` 在接受變更時就檢查：變更後的答案若超過 4,194,304 bytes 而且比變更前大，就不接受。量法與 save-quiz-draft 相同，都是答案 map 的 compact JSON 的 UTF-8 長度；前端以分題的快取計算，結果與直接序列化逐位元組相同。不讓草稿變大的變更一律接受，即使草稿已經超過上限，所以使用者永遠可以復原或清除來騰出空間。

被拒絕時，手寫題在畫布旁顯示原因；頁面上方的訊息區同時顯示「整份作答已達雲端草稿的大小上限，剛才的變更沒有套用。」，下一次被接受的變更會把它清掉。打字題與選擇題沒有自己的訊息，只有頁面上方這一則（見 Known limitations）。

## Migration and rollout

Repository 的 migration 由 18 個增為 19 個。新的 `20261013142522_drawing_point_budget.sql` 以 `create or replace` 重新定義 `private.v4_strokes_shape_valid`，與上一次定義它的 migration 相比只差兩行：筆數的比較由 `> 256` 改為 `> 16000`，取樣點的比較由 `> 6000` 改為 `> 32000`。沒有新的表、欄位、索引、policy 或 grant，沒有資料搬移。

本機驗證（Supabase CLI 啟動的本機資料庫）：前 18 個 migration 依序套用後，新的 security.sql 在舊函式上如預期失敗（「FAIL stroke ceiling is inclusive」）；套用第 19 個之後，函式的 oid、owner、language、volatility、security definer、search_path、ACL、參數與回傳型別都與套用前相同，定義 47 行中只有上述 2 行不同；完整的 security.sql 通過並 rollback 自己的測試資料。邊界測試：16,000 筆接受、16,001 筆拒絕；32,000 點接受（跨筆累計）、32,001 點拒絕；舊上限內未取整的圖仍接受。

順序是「放寬的一方先到」：先套用 migration，再部署五個 Edge function，最後才是 Pages。舊的前端自己只產生 256 筆／6000 點以內的圖，所以前兩步完成之前與之後都照常運作；新的前端要等資料庫與 Edge 都放寬之後才上線。Migration 排在最前面，是因為資料庫的檢查發生在正式提交：若它還沒放寬而 Edge 與前端已經放寬，超過舊上限的草稿存得進去，提交時才失敗。

**資料庫與 Edge 的上限只進不退。** 一旦有答案超過舊的上限，再把上限調低會讓那些答案無法再儲存、評分或顯示，所以這個 migration 不 rollback。前端可以單獨收緊：它可以在接受新筆畫時採用更低的門檻，不需要 migration。

舊前端的行為（例如放寬之後仍開著舊版頁面的分頁）：它讀到超過自己上限的草稿時不會載入；已經開著的頁面會停止同步並顯示「作答資料格式不符，已停止同步並保留本機內容。」，不會覆寫、刪除或提交它讀不懂的草稿；超過上限的已提交作答顯示為無法讀取。這是以新的程式碼模擬「上限較低的 client」測試的結果。

## Measurement

**所有數字都來自合成筆畫、本機與桌面的 headless 瀏覽器。沒有 iPad、Apple Pencil 或觸控的實機資料，也沒有 production 的數據。** 模型是為了量成本而設計的，不代表使用者的筆跡；量測包含了超過新預算的形狀，用來看成本如何成長。

模型：`cjk` 是每筆約 4 個點的短筆畫；`long` 是每筆約 40 個點的長筆畫；`dots` 是每筆一個點；`taps` 是每筆兩個相同的點。

- 只用筆寫滿一張畫布（1,295 筆、9,305 點、geometry 4.6%）：30＋31 = 61 ms。

## Known limitations

- **沒有實機資料。** 所有成本與效益的數字來自合成筆畫、本機與桌面的 headless 瀏覽器；沒有 iPad、Apple Pencil 或觸控的錄製與驗證。32,000、16,000、75% 與「一般筆畫」的定義都是判斷。
- **放開一筆的時間隨取樣點增加。** 靜止的畫布要完整重畫一次；量到的數字見 Measurement。在較慢的裝置上，接近上限時放開之後緊接著的下一筆，開頭的取樣可能被瀏覽器合併。
- **同步時主執行緒的工作隨草稿變大**：約 1／2／4 MiB 時為 59／113／224 ms（既有的程式路徑，本機）。
- **同步的流量沒有改。** 每次停筆約 0.8 秒就上傳整份草稿；save-quiz-draft 每次都重新檢查每一題，資料庫每次刪除並重寫全部答案列。以五種合成的手寫模型估算，13 或 26 題都寫滿（或寫到 4 MiB 的上限為止）的一場練習，上傳合計約 0.5–6.3 GiB；這個估算假設每 8 筆上傳一次，**這個假設是猜測，沒有資料支持**，也沒有計入下載。實作前告知 human 的粗估是約 3 GiB。
- **整份草稿 4 MiB 的上限沒有改。** 題數多而每題都寫得多時，會先碰到它而不是單題的預算。手寫題最多的題庫是 26 題：合成模型中，每題都寫滿一張畫布時五個模型有四個超過 4 MiB，也就是寫不完；13 題的題庫是兩個超過。
- **本機快取。** localStorage 的配額量到的是每個 origin 約 524 萬個字元；接近 4 MiB 的草稿加上其他草稿或備份會超過它。超過時頁面顯示無法儲存本機進度，作答仍被接受、同步與提交照常，但那段期間的內容只在記憶體與雲端。Recovery archive 不會自動清除。
- **正式提交的 CPU。** Supabase 文件記載 Edge function 每個 request 的 CPU 時間上限是 2 秒（不含 async I/O），超過時回應 546。單題在 geometry 預算附近的 rasterize 加 PNG 在本機約 0.2–0.3 秒，13 題都如此時合計約 3.2 秒、26 題約 6.5 秒；只用筆寫滿的 26 題約 1.6 秒。Geometry 預算沒有改，所以前一種情況在 v1.10.2 的上限下就可能發生；筆寫得多的情況因為預算放寬而變得可能。提交時資料庫另外要檢查全部保存的答案（見 Measurement）。Production 沒有數據。提交被中斷時作答仍是草稿，重試不會重做已完成的題目。
- **PNG 大小的壓力測試只有兩個形狀**，最大的是上限的 29%；不是上界的證明。
- **資料庫與 Edge 的上限只進不退**，見 Migration and rollout。
- **舊版頁面**：放寬之後仍開著的舊版分頁，遇到超過它上限的草稿會停止同步，需要重新整理取得新版。
- **放開時的重複取樣點（既有行為）。** 放開的位置與最後一次移動相同、且最後一段長於 24 個邏輯單位時，筆畫的終點會保存兩次。在 Chromium 上，最細的筆因此在放開前後筆尾相差 2 個像素；WebKit 沒有差別。v1.10.2 的行為相同；為了讓保存的筆畫逐值不變，這次沒有改。
- **整份草稿已滿時，打字題與選擇題的原因只出現在頁面上方的訊息區**，使用者捲到下方時看不到；那一則訊息後面帶著訊息區既有的「查看本機練習備份」連結，與這則訊息無關。手寫題在畫布旁有自己的訊息。建議之後改進。
- **容量提示在 75% 以下不顯示**，是實作時的選擇。
- **WebKit 的取樣回歸有一項未通過**，原因與判斷見 Browser evidence。
- **看得見的手寫筆跡的正式提交與 AI 評分**，在 production 仍然沒有 end-to-end 的證據；這個版本是否補上，取決於 human 對 provider canary 的決定。
- v1.10.2 記錄的其他限制仍然適用：容許誤差與最長線段是判斷；筆畫進行中若失去 pointer capture，畫布會就地 commit 當時的筆畫；筆停在原地不動時每 128 個取樣多存一個點；有幾個既有測試離 5 秒的 timeout 很近。

## Release-process notes

以下皆為 non-blocking 的記錄，不是 release blocker。

1. Human 原本被請求在兩組上限數字之間選一組；human 改為要求先做設計分析，那個選擇因此作廢，上限由分析的結論決定並經 independent reviewer 同意。
2. 設計分析中有兩種瀏覽器量測方法被捨棄（一種在 Author Preview 量、一種從頁面外量時間），改為在練習頁內、圍著應用程式自己的事件處理計時；捨棄的結果沒有被引用。
3. 進行中的畫法第一版把離屏的圖放在每一張畫布各自的元件裡，後來改為整頁共用一張。
4. 被接受的一筆只重畫一次，是在量到放開的時間之後才加入的；加入後像素比較與互動量測都重跑。
5. 量測時曾把一個臨時的測試檔放進 repository 的目錄再刪除，independent reviewer 要求之後不要這樣做。
6. 拒絕訊息中的數字在第一輪瀏覽器驗證之後改為千分位，與提示行一致；之後 gates 與全部瀏覽器情境在最終的 tree 上重跑，第一輪的輸出不作為證據。
7. 測試頁的一項比較第一次沒有通過：它拿「最後一次移動後」與「放開後」的畫面比較，而放開會多存一個點（見 Known limitations）。改為與「放開前那一筆」的獨立重畫比較；產品的行為沒有改。
8. 互動時間在同一個工作階段量了兩組，後一組整體較高（量測時本機有其他工作在跑）；本文件只引用後一組，它是在最終的 tree 上量的，並且包含 base 的對照。
9. 同步流量的估算在整理本文件時以腳本重算為一個範圍；先前告知 human 的單一數字是粗估。
10. 本機環境的變更：為了本機資料庫驗證啟動了 Docker Desktop；為了 WebKit 的驗證在 Playwright 的快取安裝了 WebKit。
