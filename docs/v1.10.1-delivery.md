## Reported symptom

Calculation 題使用「手寫」模式時，畫布上看得到完整的最新筆跡，但提交後顯示、保存與評分所用的筆跡只到先前某個中間狀態：最後一段或最後幾段筆跡沒有進入正式提交結果。

## Investigation

資料流：DrawingCanvas（本地的已完成筆畫與 controlled `strokes` prop）→ `onChange` → CalculationAnswerEditor（兩個 mode buffer）→ QuestionInput → QuizPage 的 `answerQuestion` → practice store 的 `answer()` → schema-2 draft reducer（驗證整份答案）→ store 的 attempt → 800 ms debounce 後 `save-quiz-draft` → 提交時先同步完成進行中的筆畫，再由 store 的 `submit()` 等待進行中的儲存、再儲存一次、以 CAS 比對後呼叫 `submit-quiz`。Browser 只送 `requestId`／`attemptId`／`expectedUpdatedAt`；server 以它自己保存的 draft 評分。所以正式提交的內容就是 store 在該 CAS 當下的 attempt，result／history 再從 server 的紀錄重建。

在 v1.10.0（`b5a1b3f…`）上以真正的 DrawingCanvas、store 與記憶體 server 逐一重現：

| 情境 | 畫面上的筆畫 | 提交的筆畫 | 結果 |
|---|---|---|---|
| A 最後一筆放開後立刻提交（含 D：連續快速多筆） | 12 | 12 | 正確 |
| B autosave 的 debounce 尚未執行就提交 | 3 | 3 | 正確 |
| C 較舊的儲存仍在進行，再畫一筆後提交 | 3 | 3 | 正確（儲存兩次，依序為 2、3 筆） |
| E 手寫 → 打字 → 手寫，再畫一筆後提交 | 3 | 3 | 正確 |
| 筆數超過儲存上限：畫 300 筆 | 300 | 256 | **少 44 筆，沒有任何提示** |
| 取樣點超過儲存上限：70 筆共 7000 點 | 70 筆 | 60 筆／6000 點 | **少 10 筆，沒有任何提示** |
| 儲存已被 server 套用但回應遺失，再畫一筆後提交 | 3 | 2 | **少最後一筆** |
| 提交進行中在畫布再畫一筆，該次提交失敗，再提交 | 3 | 2 | **少最後一筆** |
| 其他分頁或裝置改寫草稿後，本頁再畫一筆並提交 | 本頁的 3 筆 | 對方的草稿 | **提交了使用者沒有看到的內容** |

一般的 debounce 與 in-flight race（A、B、C、D、E）在 v1.10.0 的 store 已經正確：`submit()` 會等進行中的儲存、再儲存一次，並在送出前比對 server 的內容與版本。這是調查結論，相關的 regression 測試在舊版本也通過，沒有為了讓它們先失敗而改寫。

Root cause 有兩處：

1. **畫布可以顯示答案沒有收下的筆跡。** DrawingCanvas 以本地的已完成筆畫繪圖，只有 controlled prop 換了才重設，而 `onChange` 沒有回傳值。當答案的 owner 丟棄一次更新時 prop 不會變，畫布就一直顯示 owner 沒有收下的筆跡。Owner 丟棄更新的情況有兩種：(a) schema-2 draft reducer 驗證失敗時回傳原 draft，沒有任何訊號，筆畫超過手寫儲存上限（每題 256 筆、6000 個取樣點，或 geometry 預算）即屬此類；(b) store 在提交進行中、已停止、schema 變更或非作答狀態時直接忽略更新。
2. **`submit()` 會提交被換掉的草稿。** `submit()` 內的同步若發現 server 版本與本地不同，會改用 server 的草稿（本地變更封存到本機練習備份），之後照樣提交。儲存已被套用但回應遺失時，server 上那一版其實是這個頁面自己較早送出的內容；其他分頁或裝置改寫時，被提交的則是對方的草稿。

哪一個原因對應回報者實際看到的現象，沒有 production 資料可以佐證。以每個畫面更新一個取樣點估算，6000 點大約是 60 Hz 下 100 秒、120 Hz 下 50 秒的落筆時間，較長的手寫推導有可能碰到上限；「上限是回報症狀的主因」是推論。

## Submit-boundary contract

提交邊界：正式提交的手寫內容等於使用者按下提交時畫布上已完成的筆跡。

1. 每一次答案更新都有同步的結果：`accepted`、`limit`（被儲存上限拒絕）或 `rejected`（其他原因沒有收下，例如作答鎖定中）。
2. 畫布只保留被接受的變更。沒有被接受時，畫布還原為已接受的筆跡並顯示原因；被拒絕的只會是這一次的新變更，已接受的筆畫不會消失。
3. 提交進行中，畫布不接受新的筆畫。
4. 提交時仍在進行的那一筆（pointer 還沒放開）會先被完成並納入；之後同一個 pointer 的事件不再加入筆跡。若這一筆在完成時被拒絕，提交不會進行，頁面顯示原因。
5. 提交只會送出按下提交時 store 持有的那一份草稿。同步之後若這份草稿已被不同的 server 草稿取代，不提交，並請使用者確認目前的答案。
6. 較舊的儲存不會把較新的本地內容換掉：server 的新版本若等於這個頁面自己送出但尚未確認的內容，視為自己的儲存已套用，只採用新版本、保留本地較新的答案並再儲存。其他 client 的內容不適用這條，仍依既有設計由 server 版本優先。

Draft persistence 與正式提交是兩個不同的 contract：草稿是否已同步到 server，不影響正式提交必須等於畫面上已完成的筆跡。

## Known limitations

- **手寫儲存上限沒有改變**：每題最多 256 筆、6000 個取樣點，另有 geometry 預算；資料庫也有同樣的檢查，提高上限需要 migration 與 human 的決定，本次沒有處理。達到上限後使用者無法再加筆畫，只會看到提示，需要先復原或清除部分筆畫。「上限是回報症狀的主因」是推論，沒有 production 資料佐證。
- 上限提示只寫出筆數與取樣點數；超過 geometry 預算時顯示同一句。
- Client 只檢查單題的上限。整份草稿另有 `save-quiz-draft` 的請求大小上限與資料庫的大小上限；多題都接近單題上限時儲存可能失敗，此時提交會停在一般性的錯誤訊息。
- 畫圖題（question type drawing）沒有註冊提交前的完成步驟，這是既有行為：提交時尚未放開的那一筆不會被納入，而是在提交開始後被拒絕並顯示提示。
- 已送出但尚未確認的儲存快照只存在記憶體。頁面重新載入後無法辨認自己已被套用的儲存，本地較新的內容會依既有設計進入本機練習備份，頁面顯示 server 的草稿；畫面與提交仍然一致。
- 其他分頁或裝置改寫草稿時，本頁未同步的筆畫依既有設計進入本機練習備份，不會留在畫布上。
- Author Preview 沒有上限：preview 可以畫超過正式練習會接受的筆畫，不會看到提示。
- Schema 1 的作答路徑不在記憶體內驗證上限，行為未改。
- DrawingCanvas 與 CalculationAnswerEditor 兩個元件的 `onChange` 型別仍接受不回傳值，並視為接受；正式路徑的呼叫端型別要求回傳結果。
- 指標輸入的證據來自 Playwright 的滑鼠與測試環境的合成事件；沒有 iPad、Apple Pencil 或觸控的實機驗證。
- 沒有付費 provider canary（classifier 標記為需要，human 豁免）。**看得見的手寫筆跡在 production 沒有這個版本的 end-to-end 證據**：production canary 提交的是只含橡皮擦筆畫的作答，驗到的是「提交當下的作答狀態完整到達 server 並被保存」，沒有驗到看得見的筆跡的提交、rasterize 後的圖、AI 評分或結果頁的重建。AI 評分路徑的程式本次沒有變更。
- Production canary 的範圍：一個既有的 canary 帳號、一份題庫、一題、一次提交、滑鼠輸入、desktop Chrome、一個視窗尺寸（1424×905）。
- Production canary 的 provider_calls 0 是由回應內容與 source 推得的；mutation 的範圍沒有 SQL 證據，依據是瀏覽器端的 request 紀錄、application 自己的讀取與 source。
- Canary 帳號多了一筆已提交的作答（0 / 100），並保留在 production；兩次登入建立的 session 沒有登出，本機的暫存 browser profile 已刪除。
- 每次成功提交後，本機 cache 會把提交前的草稿封存一份到本機練習備份，這是既有行為，本次沒有修改。
- **既有的 CI 風險（本次沒有處理）**：整套測試中曾經 timeout 的既有測試有四個——`App.test.tsx` 的「restores drafts on remount…」與「warns about unanswered questions…」、`AuthorPage.test.tsx` 的「rejects duplicate revision…」、`Auth.test.tsx` 的「validates registration…」。其中最慢的「restores drafts on remount」離 vitest 預設的 5 秒 timeout 很近。Release prep 期間（2026-10-12）在本機觀察到的整套測試失敗全部列在這裡：
  1. `release:check` 第一次執行時 test gate 失敗：只收集到 1,573／1,576 個測試。當時只有這一個 suite 在執行；測試輸出沒有被工具保留，**原因不明**，之後沒有再出現。
  2. 單一 suite 連續執行的前 5 次中有 2 次失敗，都是「restores drafts on remount」test timeout（5,245 ms 與 5,101 ms）。當時沒有其他 suite 同時執行。
  3. 兩個 suite 同時執行時的失敗。上述的重複執行沒有如預期停止，與之後的 base／candidate 比較量測重疊：重複執行的第 9–13 次全部失敗；比較量測中，純 v1.10.0 的 source 5 次失敗 2 次，本 candidate 5 次失敗 2 次。這些失敗全是 test timeout（5,005–5,463 ms），涉及上述四個既有測試；其中四次還包含本次新增、當時尚未改寫的「第 257 筆」測試（5,014–5,463 ms）。這個 base／candidate 比較的十輪中，前九輪全程與最後一輪的開頭都有另一個 suite 在同一台機器上執行，不是單一 suite 的量測。

  通過的紀錄：第 1 項之後、第 2 項之前，同一棵 tree 上單一 suite 連續 7 次通過；上限測試改寫後的最終 tree 上，單一 suite 連續 8 次通過，independent reviewer 其後另外量得連續 21 次通過。

  單一 suite 執行時的耗時：最終 tree 上連續 6 次整套執行中，最慢的「restores drafts on remount」為 4,052–4,245 ms；independent reviewer 的 20 次連續執行量得四個測試分別為 3,677–4,917 ms（restores drafts）、3,495–4,124 ms（rejects duplicate）、2,845–3,447 ms（warns about）、1,990–2,777 ms（validates registration）。兩個 suite 同時執行時，四個都曾超過 5 秒。v1.10.0 的兩次 CI 都通過：test step 為 30 秒與 50 秒，這四個測試依同樣順序為 1,576／1,965／1,405／432 ms 與 3,358／3,303／2,769／706 ms。這個版本的 candidate CI（run 38192246973）也通過：test step 40 秒，四個測試依同樣順序為 2,072／2,622／1,844／528 ms。

  這些測試與本次變更無關，沒有修改，也沒有調整 timeout；exact CI 因它們 timeout 的風險與 v1.10.0 來自同一來源，之後的 closure commit CI 也有同樣的風險。第 2 項顯示單一 suite 也會 timeout，所以這不是只有在外部負載下才會發生的現象。本次新增的三個上限測試原本各要畫 256 筆或 6000 個點；其中只有「第 257 筆」測試在第 3 項的條件下實際 timeout 過。三個都已改為上述先放入草稿的做法，改寫後在整套執行中為 0.4–0.8 秒。
