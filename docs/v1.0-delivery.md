## 3. Account recovery architecture 與一致性模型

`account-recovery-code` 是 authenticated endpoint：platform `verify_jwt=false`，handler 使用 `withSupabase({ auth: 'user' })`，再以 JWT `session_id` 與 authenticated user ID 呼叫 service-only RPC，確認 `auth.sessions` 尚有效。Browser 不能選擇另一個 user ID。Status 只回 active／createdAt；generate 才回一次 raw code。

`recover-account` 是 public endpoint，只接受 username、code、新密碼及 CAPTCHA token。它 normalize username、驗證 payload／密碼、檢查 CAPTCHA、消耗 durable quota、以 digest claim 帳號，再由 server Auth Admin 更新密碼。成功只回 success，沒有自動建立 session。

兩個交易邊界如下，並非把 RPC 與 HTTP request 當成同一交易：

1. Claim RPC 鎖定 recovery row，從 `active` 轉為 `claiming`，建立 UUID claim 與 **5 分鐘 TTL**。仍在 TTL 的 claim 不能重複取得。
2. Auth Admin 在自身 PostgreSQL transaction 更新密碼與 app metadata。實際 Auth implementation 分兩次 SQL 寫入；新的 **deferred constraint trigger** 在該交易结束時讀取最終 user row、驗證密碼確有更新、claim 符合且未過期。
3. Trigger 在 Auth 的同一交易中把 code 轉 `used`、移除暫存 marker、刪除該帳號 sessions。任何驗證失敗會 rollback 密碼及 consume，避免只完成一半。
4. HTTP 失敗／timeout 時，release RPC 與 consume 使用同一 row lock。若已 committed used，回報成功；否則釋放為 active。晚到的 Auth write 因 claim 已釋放而整筆 rollback。若 release 也暫時失敗，claim 可於 TTL 後重新取得。

這依賴 Supabase Auth 把 password 與 metadata 寫在同一 DB transaction，已用 live E2E 與分段 SQL rollback fixture 驗證。未來升級 Auth 後應重跑；不是跨任意服務的分散式交易保證。可參閱 [Supabase Auth Admin implementation](https://github.com/supabase/auth/blob/master/internal/api/admin.go)。

最初的 per-statement trigger 在 live E2E 回 503；失敗時碼安全釋放、暫時旗標移除。保留已套用 migration，新增第二支 migration 修正，沒有修改 migration 歷史。

## 4. Recovery code security 與 UX

- Web Crypto `getRandomValues` 產生 **16 bytes／128 bits entropy**，八組四位十六進位字元。
- private DB 只保存 SHA-256 digest；沒有可逆加密或 raw code。回應 no-store，payload 上限 4 KiB。
- raw code 只出現在 generation response 與該頁記憶體；沒有寫入 logs、repository 或 localStorage。
- 註冊成功後顯示保存提醒、Copy、Download text，使用者需勾選「我已保存復原碼」才可繼續。不自動下載。
- Reload／再次進 Account 只顯示是否設定。更換先確認，舊碼立即失效；讀取狀態前不能按生成，避免誤把 rotate 當首次建立。
- 成功 recovery 後舊碼立即失效；提示正常登入並產生新碼。沒有 email reset 假流程。
- 不存在的 username、錯碼、已使用碼均回同一訊息「復原資訊無效或已過期。」

Recovery Code 是 bearer secret；遺失密碼且沒有有效碼就不能自行恢復。明確下載或複製後的檔案／剪貼簿由使用者保管。

## 6. Password policy、hint 與 session

前端／Recovery Edge 新密碼至少 8 字元、至多 72 UTF-8 bytes。遠端原為 minimum 6，已提高到 **8**，沒有弱化 policy。Account change-password 先驗證目前密碼，再 `updateUser({ password, current_password })`；遠端 **Require current password when updating 已啟用**。Live 已確認：缺 current／錯 current 被拒，正確 current 成功，舊密碼不能登入，新密碼可登入。

Password Hint UI 明示「提示不能重設密碼」，只作記憶輔助並連到 Recovery Code。Synthetic email 只用於 Auth 內部識別，Account 不顯示它。

Restore 不只信 local session 或 getUser：另查 recovery management endpoint 綁定的 `auth.sessions`。過期、撤銷不被當成 authenticated；15 秒 timeout／網路錯誤不刪本機答案。已載入草稿可離線輸入，重新載入需連線驗證。Logout 會傳播到同 browser context 的其他 tabs，保留 owner-scoped cache。

限制：刪除 sessions 不會讓所有已發 JWT 在每種 Supabase API 立即失效；部分 API 仍可能接受 token 到一小時 expiry。不能把 UI/session-management 的即時拒絕說成 universal JWT revocation。

## 9. Practice recovery UX 與 sync hardening

`#/recovery` 只列目前帳號在此裝置的備份：quiz ID、縮短 attempt ID、時間與原因。Raw JSON 須主動檢視；可 Export JSON、確認 Delete，或嘗試安全還原。
